# 《鈴音の夜祭り》答辩准备：可能被问的问题与回答（技术细节）

数字均核对自 2026-11-05 的源码（`SuzuneMatsuri/Source/SuzuneMatsuri/Matsuri/`，下文简写为源码路径）。性能数据来自本机（2560×1600 屏幕）上的 `MatsuriPerf.*` 探针实测。回答尽量“先一句结论，再给细节”，答辩时可以只说第一句，被追问再展开。

---

## 一、一分钟项目介绍（开场用）

> 《鈴音の夜祭り》是用 **Unreal Engine 5.8 + C++** 做的第一人称动作游戏。玩家从三位角色（巫女、忍者、猫又）中选一位，在三层**程序生成的迷宫**里收集金币、对抗妖怪，最后在神社庭院里与九尾狐玉藻进行**东方 Project 风格的弹幕 Boss 战**。
>
> 技术亮点有三个：
> 1. **Boss 会学习**：选招用三层决策——大模型（DeepSeek）通过上下文学习（ICL/ICRL）读历史战斗记录做决定，本地还有一个自己实现的 **LinUCB 在线学习器**，网络不通时也能自己学。
> 2. **大规模弹幕**：子弹不是 Actor，而是数据数组 + 连续碰撞检测 + 实例化渲染，同屏两百多颗子弹保持约 60 fps。
> 3. **工程化**：约 2 万行游戏代码、7700 行测试代码、107 个自动化测试（含端到端测试自动试玩），美术用 AI 生成 3D 模型 + 购买的素材包，全部可脚本化导入。

## 三、整体架构

**Q1：项目的整体架构是怎样的？**
分三层：
- **纯规则层**（`F` 开头的 C++ 结构体）：一局的状态 `FMatsuriRunState`、迷宫 `FMatsuriMaze`、学习器 `FMatsuriBossLearner` 等，不依赖场景，可以直接单元测试。
- **跨关卡服务层**（`UGameInstanceSubsystem`）：`UMatsuriRunSubsystem` 保存整局数据和存档，`UMatsuriMusicSubsystem` 管背景音乐。它们挂在 GameInstance 上，换地图不会销毁。
- **场景层**（GameMode、Actor、Component）：`AMatsuriFloorGameMode` 是每张地图的“导演”，负责生成关卡、倒计时、受伤、结算；Boss 关的 GameMode 继承它。

举例：玩家受伤会依次经过 `FloorGameMode::HurtPlayer`（无敌时间、死亡回放）→ `RunSubsystem::HurtPlayer`（广播给 UI）→ `RunState::Hurt`（真正扣数字）。

**Q2：为什么这样分层？**
三个好处：① 规则可以不开游戏就测试（比如“受伤时先消耗狐之祝福”）；② 换关卡时数据不丢；③ 每层职责单一，改 UI 不会动到规则。

**Q3：用了哪些 UE 模块？有没有第三方库？**
只用 UE 自带模块：Engine、EnhancedInput（输入）、Niagara（粒子）、UMG/Slate（界面）、HTTP 和 Json（调大模型、存档）、MediaAssets（播视频）。**没有第三方 C++ 库**，LinUCB、迷宫生成、弹幕碰撞都是自己写的。外部只有两个在线服务：Tripo（生成 3D 模型）和 DeepSeek（Boss 决策）。

**Q4：游戏流程怎么在关卡之间流转？**
标题地图 → `Flow::StartNewRun` 初始化一局 → 加载 1F → 达标后选御守 → 下一层 → … → Boss → 胜利/失败。切换时先显示加载画面，再用 `OpenLevel`。延时挂在引擎核心计时器 `FTSTicker` 上，因为结算菜单会暂停游戏，暂停时普通计时器不走。

## 四、玩法规则

**Q5：分数、HP、弹药、大招是怎么管理的？**
都在 `Core/MatsuriRunState`。HP 基础 200、上限 600；每层补一次“狐之祝福”，受伤时先抵消一次。弹药容量 = 武器容量 × 御守倍率。大招能量：拾取每分 +0.02，造成伤害每点 +0.04，满 1 才能用。

**Q6：三个角色有什么区别？**
配置表在 `Core/MatsuriHeroes.cpp`：
- 樱（巫女）：+50 HP，蓄力弓（12 发，可穿透），技能是结界、驱邪、大祓。
- 铃音（忍者）：移速 +15%、二段跳，三发扇形手里剑（30 发），技能是瞬身、分身、影缝。
- 澪（猫又）：银币加分，会弹跳的铃铛（20 发），技能是招财猫、投钱（花 5 分）、大招吸取掉落 + 双倍掉落。

**Q7：御守（升级）怎么随机？**
用“本局种子 + 层数”构造确定性随机流，洗牌 8 种御守取 3 个。好处是同一局的选项可复现，方便调试和测试。

**Q8：存档怎么做的？**
UE 的 `USaveGame` 写 `.sav`，同时写一份 JSON 方便查看。测试用独立存档槽 `MatsuriRecord_Test`，不会污染玩家成绩。

## 五、迷宫与关卡生成

**Q9：迷宫是怎么生成的？**
`Level/MatsuriMaze.cpp`，四步：
1. 所有格子先封墙（每格 4 个二进制位记四面墙）；
2. **递归回溯算法**（用显式栈实现）随机挖通道，得到所有格子连通、无环的“完美迷宫”；
3. 按概率再拆掉一些墙形成环路（1F 25%、2F 18%、3F 12%），避免只有一条路；
4. 打通 2×2 的小广场用于战斗。

随机数用 `FRandomStream`，**同一个种子永远生成同一个迷宫**（`matsuri.Seed`）。

**Q10：为什么选递归回溯而不是 Prim 或 Kruskal？**
递归回溯生成的通道长、分叉少，“走迷宫”的感觉强；再用“拆墙成环”补回多路线。Prim 生成的短死路很多，不适合第一人称。

**Q11：金币和敌人怎么摆放，保证不重叠、公平？**
`MatsuriFloorLayout.cpp` 用占位采样器：每个候选点检查与出生点距离、与障碍和已放物品是否重叠。金币放在非起始格，敌人和陷阱要求离出生点更多格（按迷宫通道步数，不是直线距离），避免开局被打。

**Q12：场景装饰怎么避免穿模？**
`MatsuriFloorDecor.cpp` 维护一张“占位表”，每个装饰放下前检查它的包围盒是否会插进墙、盖住金币或堵住门口，放不下就跳过。装饰本身没有碰撞，碰撞仍由原来的灰盒方块负责；装饰替代某个方块时，方块隐藏但碰撞保留。这样**美术怎么改都不影响玩法**。

## 六、战斗系统

**Q13：射击是怎么实现的？准星为什么准？**
从准星向前做射线检测（`LineTraceSingleByChannel`）得到命中点，子弹从武器尖端飞向这个点，所以第一人称下“准星指哪打哪”，不会因为枪口偏移而打歪。

**Q14：子弹的物理是怎么做的？**
玩家子弹是 Actor，用 UE 的 `UProjectileMovementComponent` 处理飞行和反弹。箭和苦无撞墙会插进去（生成几秒后消失的模型），铃铛和金币反弹。命中妖怪用重叠检测，之后依次尝试：弹跳到下一个目标 → 消耗穿透次数 → 销毁。

**Q15：河童的黄瓜怎么瞄准玩家？**
先按玩家当前速度预测提前量，再用抛体公式反推发射角（`LobDirection`），取较低的那条抛物线；理论不可达时用 45° 兜底。

**Q16：近战怎么判定？**
纯数学：距离在范围内、高度差够小、角度在前方扇形内（贴身时不看角度）。比物理检测便宜，也更可控。命中会击退、眩晕，并拍掉飞来的黄瓜。

**Q17：特效多了会不会卡？**
自己写了特效**对象池**（`Combat/MatsuriFx.cpp`）：特效结束不销毁，隐藏后放回池里复用；进关时预热，第一次挥刀不会因为创建对象而卡顿。Niagara 模板也在进关时预加载。

## 七、敌人 AI

**Q18：妖怪 AI 用的是行为树吗？**
不是，是自己写的规则 AI（`Enemies/MatsuriYokaiBrain.cpp`），每种妖怪一个纯函数“看到什么 → 做什么”：
- 灯笼妖：被玩家看着时慢慢挪，没看着时潜行，近了就突袭（类似“一二三木头人”）；
- 伞妖：在拐角埋伏，玩家靠近就扑；
- 河童：在周围多个半径、多个方向采样候选点，判断“能不能走到、玩家看不看得到”，分出躲藏点和探头点，冷却时躲、准备好就探头投掷。

**Q19：为什么不用行为树或 StateTree？**
三种妖怪逻辑都很短（几个分支），写成纯函数更直观，而且能直接写单元测试（给定感知输入，断言输出的动作）。行为树更适合复杂、需要策划在编辑器里调整的 AI。

**Q20：寻路为什么不用 NavMesh？**
迷宫本身就是格子图，用 BFS 从目标格算出每格到目标的步数，下一步走向步数更小的相邻格，路点放在门口稍往里。好处：① 迷宫是运行时生成的，不用每次重建导航网格；② 结果确定、可测试；③ “感知范围”也能按通道步数算，墙后的妖怪不会隔墙追人。

**Q21：“玩家有没有看见我”怎么判断？**
两个条件同时成立：怪物在玩家视野锥里（方向点积），并且两者之间射线无遮挡。

## 八、Boss 战与弹幕

**Q22：Boss 的整体流程？**
`BossGameMode` 搭庭院并生成玉藻 → 玉藻每帧观察玩家、推进状态机 → Brain 决定下一招 → `BossSkills` 把招式翻译成发弹时间表 → `DanmakuField` 移动子弹、检测碰撞、扣血 → Brain 给这一招打分、存记忆、更新学习器。

**Q23：Boss 的状态机有哪些状态？**
开场、换阶段、施法、战败。三条血是同一个总血量（150），在 2/3 和 1/3 处换阶段；换阶段时清屏、短暂无敌、说台词。阶段越高两招间隔越短：1 s → 0.7 s → 0.45 s，弹速倍率 1 → 1.05 → 1.15。

**Q24：六种技能？**
环、螺旋、追踪（鬼火）、扫尾、雨、幻影。第 1 阶段只有前三种，第 2 阶段加扫尾和雨，第 3 阶段加幻影。每招有 4 个 0～1 参数，映射成轮数、速度、缺口大小等。

**Q25：为什么子弹不用 Actor？**
Actor 有组件、Tick、碰撞等开销，几百个就会明显卡。这里每颗子弹只是数组里的一个结构体（位置、速度、半径、寿命、伤害），每帧统一计算；渲染按“外观 × 技能”分组，每组一个 `UInstancedStaticMeshComponent`，几百颗子弹只需几次绘制调用。上限 1400 颗。

**Q26：高速子弹会不会穿过玩家？（连续碰撞检测）**
不会。不是只看每帧末尾的位置，而是用“子弹相对玩家的运动”求这一帧内最早接触的时刻（解一元二次方程），所以高速子弹、玩家冲刺都不会“隧穿”。掩体也一样：把方块按子弹半径扩大，求线段最早进入盒子的时刻，再和打中玩家的时刻比先后。

**Q27：为什么受击判定这么小？**
仿东方 Project：受击球半径只有 22 cm（比身体小得多），擦弹范围 90 cm。擦弹会给大招充一点能量，鼓励“贴着弹走”。

**Q28：子弹伤害怎么定？**
按密度算（`BossSkills::BulletDamageFor`）：一招子弹越多，单颗越弱，例如环 10～14、追踪 18～24。这样“铺满屏的弹幕”和“少量精准追踪弹”威胁大致相当。帧率低时会把这一帧应该发出的所有轮次补齐，不会漏发。

**Q29：钩索怎么做的？是物理绳吗？**
不是物理绳。在 35 m、准星 12° 范围内找钩环，射线确认无遮挡；然后把角色移动模式切到飞行（`MOVE_Flying`），每帧设置朝钩环的速度；到达或跳脱时切回下落并给一点前冲和上抬。绳子只是一根拉长的圆柱。

**Q30：庭院里的掩体？**
固定掩体（石灯、狐像、本殿）永远挡弹；4 段木栅栏挨 25 发会碎，20 秒后长回来，防止玩家永远躲在后面。

## 九、Boss 的 AI 与学习（最可能被深问）

**Q31：Boss 怎么决定用哪招？**
三层回退：
1. **大模型**（DeepSeek）：读提示词返回 JSON（技能、4 个参数、目标区域、台词、理由）；
2. **本地 LinUCB 学习器**：模型超时（6 s）、没联网、回复非法时使用；
3. **规则兜底**：当前阶段允许的技能轮流用。

**Q32：什么是 ICL 和 ICRL？你们怎么用的？**
- **ICL（In-Context Learning，上下文学习）**：从历史记录里检索与当前局面相似的案例（“当时的局面 → 用了什么招 → 结果和奖励”），放进提示词，让模型参考。
- **ICRL（In-Context Reinforcement Learning，上下文强化学习）**：把本局最近 10 招的“动作 → 奖励”放进提示词，让模型在同一局里根据反馈调整。
- 另外每局结束让模型根据整局过程改写最多 10 条“复盘笔记”，下一局放进提示词。

**Q33：相似案例怎么检索？**
把局面编码成 9 个归一化特征（阶段、玩家是否在掩体后/高处/空中、距离、弹药比例、躲掩体和待高处的时间占比），用欧氏距离找近邻，不同阶段额外加惩罚。先取 3K 个近邻，再从中取奖励最高和最低的各一半——**让模型同时看到成功和失败的经验**，避免只模仿。

**Q34：大模型真的“学习”了吗？有没有训练它？**
**没有修改大模型的权重。** 大模型的“学习”体现在提示词里：经验放进上下文，回答随之改变（这就是 ICL/ICRL 的定义）。真正有参数更新的是本地 LinUCB 学习器。这一点答辩时要说清楚，不要说“训练了大模型”。

**Q35：LinUCB 是什么？为什么选它？**
上下文多臂老虎机算法。18 个选项（6 招 × 3 组预设），每个选项维护一个 10×10 矩阵 A 和 10 维向量 b（本质是岭回归），预测“在这种局面用这招能拿多少奖励”。
- 选招：比较 `θᵀx + α·√(xᵀA⁻¹x)`，其中 θ = A⁻¹b，α = 0.6；后一项是“不确定性奖励”，鼓励多试用得少的招（探索 vs 利用）。
- 更新：A += xxᵀ，b += 奖励·x。
- 矩阵求逆是自己写的带选主元的高斯-约旦消元。

选它的原因：样本少也能学（每场只有几十招），计算量小（每次决策求 18 个 10×10 的逆，微秒级），可解释（能输出每招的预计收益），参数能存成 JSON。深度强化学习需要成千上万局，不现实。

**Q36：奖励函数怎么设计的？**
`奖励 = min(碰到玩家次数, 3) − 10 × 这招期间玉藻掉血比例 + min(0.02 × 擦弹次数, 0.5)`
- 碰到玩家是正分，最多记 3 次（避免一招刷分）；
- 玉藻被打掉血是负分（比如掉 2% 血扣 0.2）；
- 擦弹给少量正分（让玩家紧张也算“好招”）。

**Q37：（追问）奖励用“碰到”而不是“真正扣血”，合理吗？**
当前实现确实按“碰到”（Touches）计分，玩家无敌期间碰到也算。可以这样解释：Boss 的目标是“施压”，无敌只是玩家刚受伤后的短暂保护，不应让 Boss 因此认为这招没用。但也要承认局限：奖励高不一定等于胜率高。改进方向是加入整局胜负的延迟奖励，或按真正扣血（Hits）计分。

**Q38：大模型延迟几秒，会不会卡游戏？**
不会。① **异步**：HTTP 请求在后台进行，游戏线程不等；② **预取**：当前这招刚开始，就提前请求下一招，等这招放完答案通常已经回来；③ **超时回退**：6 s 内没回来就用本地学习器；④ 过期回复（请求序号对不上）直接丢弃。

**Q39：怎么防止大模型乱回答？**
`BossPrompt::ParseDecision` 校验：技能必须存在且当前阶段允许，参数限制到 0～1（非法值改 0.5），目标区域必须合法，台词和理由截断长度。另外从回复中提取 JSON 时会正确处理字符串里的花括号。不合法就用本地学习器。

**Q40：API 密钥安全吗？**
密钥只从环境变量 `DEEPSEEK_API_KEY` 运行时读取，不写进代码、存档或打包产物；没有密钥时 Boss 只用本地学习，游戏完整可玩。

**Q41：记忆存在哪？会越来越大吗？**
`Saved/BossMemory/` 下：`steps.jsonl`（每招一行）、`fights.jsonl`（每局一行）、`learner.json`（LinUCB 参数）、`notebook.json`（复盘笔记，最多 10 条，覆盖保存）。JSONL 一行一条，追加写很便宜。提示词只取最多 8 个案例，所以记忆再大，提示词长度也不变。

**Q42：演示时怎么展示六招？**
开 `matsuri.BossShowcase 1`：玉藻按顺序演示六招，且不写入记忆、不更新学习器，不会污染学习数据。

## 十、美术与渲染

**Q43：美术资源从哪来？**
- 角色、道具、妖怪：用 **Tripo**（AI 生成 3D 模型的服务）生成，Blender 脚本统一尺寸，UE Python 脚本批量导入；
- 神社场景：购买的 Fab 素材包 “Mountain Temple”（Hivemind）；
- 过场：预先制作的动画短片（mp4）。

**Q44：没有美术资源时游戏还能玩吗？**
能。所有美术通过 `Core/MatsuriArt.cpp` 按名字加载，找不到就用灰盒形状（立方体、球、圆柱）。所以开发早期就能玩，美术可以后补；关掉 `matsuri.Art` 还能对比效果。

**Q45：素材包里的本殿怎么放进游戏的？**
写了两个脚本：`dump_pack_map.py` 读出素材包演示地图里本殿 189 个零件的位置和旋转，`make_temple_prefab.py` 生成 C++ 坐标表，游戏运行时按表把本殿拼出来，放在 Boss 庭院本殿碰撞块的顶上。只存坐标数字，模型仍在购买的素材包里（素材包不提交到 git）。

**Q46：渲染用了哪些技术？**
全是 UE5 的：Lumen（实时全局光照和反射）、Nanite（高面数模型）、虚拟阴影贴图、TSR（时间超分辨率）。自己做的部分：每层的灯光主题（黄昏 → 暮色 → 深夜 → 月下，越深入越暗）、按世界坐标贴图的墙面材质（灰盒怎么拉伸纹理都不变形）、卡通着色原型（目前只用在两个角色上）。

## 十一、性能优化（有实测数据，适合讲）

**Q47：遇到过什么性能问题？怎么解决的？**
1. **画质过高**：编辑器默认 Cinematic 画质，Lumen 一项就占 24 ms。游玩时把画质上限压到 Epic、全局光照压到 High。
2. **高分辨率下掉帧**：2560×1600 下 GPU 每帧约 19 ms（超过 60 Hz 的 16.7 ms 预算），垂直同步让帧时间在 16.7 和 33 ms 之间跳，感觉“一卡一卡”。解决：按窗口高度把渲染分辨率降到约 900 行，再用 TSR 升回窗口大小（`matsuri.RenderHeight`）。**1F 从 47–52 fps 提到稳定 60 fps，Boss 从 48 提到 59 fps（235 颗弹）。**
3. **首次出现卡顿**：特效对象池预热、Niagara 和音效预加载、音乐启动时全部预加载。
4. **大量弹幕**：数据数组 + 实例化渲染（见 Q25）。
5. **落叶**：几千片落叶用实例化组件，只占一次绘制。

**Q48：怎么测性能？**
自己写的性能探针 `MatsuriPerf.Floors / MatsuriPerf.Boss`：自动走路、转身、射击、近战 15 秒，记录每帧的游戏线程、渲染线程、GPU 时间，输出平均值、p50/p95/p99 和超过 50 ms 的卡顿帧，还会导出一帧的 GPU 各阶段耗时（ProfileGPU）。用 p95/p99 而不是平均值，因为“卡”看的是最慢的那些帧。

**Q49：遇到过崩溃吗？**
遇到过一次间歇性 GPU 崩溃（显卡页错误）。从崩溃日志里的 GPU 面包屑定位到 Nanite 曲面细分（素材包材质的位移）在虚拟阴影阶段出错，关掉 `r.Nanite.Tessellation` 后修复，且实测不影响帧率。还写了压力测试 `MatsuriArt.FloorStress` 反复加载关卡来验证。

## 十二、界面与音频

**Q50：UI 是怎么写的？**
UE 的 UMG 控件，但**全部用 C++ 搭建**（`WidgetTree->ConstructWidget`），不用蓝图。共用的颜色、字体、按钮样式（含悬停/点击音效）在 `UI/MatsuriUIStyle.cpp`。刷新方式：数据类（分数、HP、弹药）订阅事件更新；时间类（倒计时、冷却、准星动画）每帧更新。好处：git 能看出改动、端到端测试能直接读界面文字；缺点：不能在编辑器里拖拽调布局。

**Q51：背景音乐怎么做的？**
`Core/MatsuriMusic.cpp`，游戏实例子系统：每个场景一首，用 `UAudioComponent` 做 1.5 秒交叉淡入淡出；设为“跨关卡保留”，加载时不断；设为“界面声音”，暂停菜单下也继续播；Boss 第三条血换曲；过关/失败播短乐句。

**Q52：音效是哪来的？**
一部分是 Kenney 的免费音效（CC0）；弓弦、铃铛、风声等用 Python + numpy 合成（`tools/audio/build_sfx.py`），ffmpeg 转码后导入。重复音效（脚步、命中）每次随机 ±6% 音高，避免机械感。

## 十三、测试与工程质量

**Q53：怎么保证质量？测试有哪些？**
107 个 UE 自动化测试：
- **单元测试**：规则（分数、HP、御守）、迷宫（连通性、确定性）、学习器、提示词解析、弹幕碰撞几何等；
- **端到端测试（22 个）**：自动启动编辑器内试玩，按步骤模拟操作并断言，例如“标题 → 1F → 过关 → 2F → Boss 各血条 → 结局 → 失败”时音乐依次正确；
- 另有性能探针、截图测试、压力测试（不在主测试集里，因为依赖显卡）。

测试使用独立的存档槽和 Boss 记忆目录，不污染玩家数据。

**Q54：有没有已知问题？**（诚实回答）
- 场景切换端到端测试（`SceneTransitions`）目前有一个断言失败（离开 1F 时没检测到加载画面），与最近的音乐和性能改动无关，还在排查。
- DirectX 11 的旧显卡上，素材包的部分屋顶和木纹材质会显示为默认灰色（材质贴图采样器超过 DX11 上限），DirectX 12 正常。
- 卡通着色只是原型。

**Q55：开发流程和工具？**
命令行脚本化：`tools/build.sh` 编译，`tools/ue_cmd.sh` 跑测试，`tools/ue_py.sh` 跑 UE Python 导入脚本，`tools/package.sh` 打包。每次改动后编译 → 跑相关测试 → 截图对比。

**Q56：怎么打包发布？**
`tools/package.sh` 调用 UE 的 `RunUAT BuildCookRun`，编译 Shipping 版、烘焙资源、打成 pak。注意点：代码按路径加载的资源（模型、音频、素材包）在配置里显式加入“必烘焙目录”，否则不会被打进包；过场视频以文件形式放在 pak 外面，因为播放器按文件路径打开。产物 1.9 GB，独立运行。

## 十四、可能的“刁钻”问题

**Q57：AI 生成的模型和音乐有版权问题吗？**
Tripo 生成的模型和自己生成的音乐用于课程作业；购买的素材包按 Fab 许可使用，不提交到仓库；免费音效是 CC0。曾发现一个来源不明的素材包（疑似转售的盗版）和一首东方原曲，都没有使用。

**Q58：如果让你继续做，最想改进什么？**
1. 奖励函数加入整局胜负的延迟奖励，让 Boss 学“赢”而不只是“施压”；
2. 用更强的检索（学习得到的相似度）替代欧氏距离；
3. 难度自适应：根据玩家水平调整 Boss 的探索系数；
4. 完成卡通着色和更多角色动画；
5. 修复上面提到的测试失败。

**Q59：哪部分最难？**
可选回答：弹幕的连续碰撞（高速子弹 + 玩家移动 + 掩体先后顺序，还要处理“致死一击后回放清屏”导致数组被改的重入问题）；或者大模型的异步预取与过期回复处理。

**Q60：你们的 Boss 和普通游戏 AI 最大的不同是什么？**
普通游戏 AI 的策略是写死的；我们的 Boss 每一招都记录“局面 → 动作 → 结果”，下一招、下一局会根据这些经验改变选择：短期靠提示词里的本局轨迹（ICRL），长期靠检索历史案例（ICL）和本地 LinUCB 的参数更新。因为“玩家待在高处的时间占比”是学习器的输入特征之一，如果某招对总在高处的玩家更有效，她就能学到在这种局面下多用它。（注意措辞：这是机制上“能学到”，答辩时不要说成已经验证过的结果。）
